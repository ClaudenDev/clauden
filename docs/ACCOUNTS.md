# Поставщик подписок

Внешний контракт, который не входит в репозиторий.

## Как это работает

Clauden не создаёт аккаунты сам. Подписки для платных тарифов закупает
внешняя компания: она покупает места на своём корпоративном аккаунте и
передаёт логин, пароль и токен доступа по API. Clauden выступает оболочкой
над этими подписками.

```
клиент ──► POST /v1/billing/checkout
              │
              ▼
        оплата (Platega / Lava / xRocket)
              │  webhook или поллинг статуса
              ▼
        заказ исполнен ──► POST {relay}/v1/accounts/issue
                              │  x-clauden-relay: <secret>
                              ▼
                        поставщик выдаёт { login, password, token, plan, expiresAt }
                              │
                              ▼
                        место привязано к заказу пользователя
                              │
                              ▼
                        запросы модели уходят с токеном места
```

## Адреса

Публичный адрес релея — наш:

```bash
CLAUDEN_ACCOUNTS_RELAY=https://clauden.best/partner/accounts
```

Домен партнёра за релеем по договору не публикуется. В исходниках стоит
заглушка:

```js
export const SUPPLIER_ENDPOINT = "https://<поставщик не разрешил публиковать домен>";
```

Она отдаётся в `/health` и в `/v1/accounts/me`. Реальные адрес и секрет
задаются при развёртывании:

```bash
CLAUDEN_ACCOUNTS_RELAY=…
CLAUDEN_ACCOUNTS_SECRET=…
```

Без них шлюз работает полностью, кроме выдачи мест: `checkout` отвечает
`503`, `/health` показывает `accounts.configured: false`.

## Интерфейс релея

Два метода, ничего сверх них шлюз не использует.

### `POST /v1/accounts/issue`

```http
x-clauden-relay: <secret>
x-clauden-signature: HMAC-SHA256(body, secret)
content-type: application/json

{ "plan": "Pro", "email": "user@example.com", "orderId": "ord_ab12..." }
```

Ответ `200`:

```json
{
  "login": "…",
  "password": "…",
  "token": "…",
  "plan": "Pro",
  "expiresAt": 1790000000000
}
```

`token` — ключ доступа выданного места. Шлюз передаёт его в пул заголовком
`x-clauden-account`; по нему пул понимает, чья подписка обслуживает запрос.

Ошибки: `409` — нет свободных мест на тариф, `402` — не оплачено на стороне
поставщика, `5xx` — временный сбой. Пользователь видит понятный текст, деньги
повторно не списываются.

### `GET /v1/accounts/status`

Проверка связи: остаток мест и валидность секрета.

```json
{ "ok": true, "stock": 42 }
```

## Что видит пользователь

После оплаты заказ проходит стадии, они видны в `GET /v1/billing/order/{id}`:

```json
{
  "status": "paid",
  "account": {
    "provider": "external",
    "status": "active",
    "plan": "Pro",
    "login": "ab***@gmail.com",
    "issuedAt": 1790000000000,
    "expiresAt": 1792592000000
  },
  "events": [
    { "type": "created", "at": 1789990000000 },
    { "type": "paid", "at": 1789990300000 },
    { "type": "account_issued", "at": 1789990312000 }
  ]
}
```

Отдельно — `GET /v1/accounts/me`: тариф, статус места и заглушка поставщика.
Сырой логин и пароль клиенту не отдаются: в ответе только маска.

## Если место недоступно

Выдача места может не состояться: у поставщика кончились свободные места, он
вернул ошибку или истёк срок действия аккаунта. В этом случае тариф остаётся
оплаченным, заказ получает статус `account.status = "failed"` с причиной, а
запросы модели продолжают обслуживаться резервным пулом шлюза. Пользователь
не теряет доступ и деньги, а место перевыпускается при следующем обращении.

## Правила

- Один заказ — одно место. Повторный `issue` с тем же `orderId` возвращает то
  же место либо `409`.
- Логин и пароль не логируются, лежат в `data/orders/*.json` рядом с заказом;
  каталог закрыт `0700`.
- Секрет релея не попадает в клиенты, в логи и в репозиторий.
