## Поток запроса чата

1. Клиент шлёт `POST /v1/chat/completions` с заголовками
   `x-conversation-id`, `x-turn-id`, `x-device-name`.
2. Шлюз проверяет токен (или API-ключ), тариф, доступность модели и лимиты.
3. Создаётся запись в журнале ходов (`turns.mjs`) — это позволяет забрать
   ответ, даже если соединение оборвалось.
4. Запрос уходит в пул (`upstream.mjs`) в формате OpenAI chat-completions.
5. Ответ ретранслируется клиенту как SSE:
   - `delta.content` — текст,
   - `delta.clauden_thinking` — размышления,
   - `delta.clauden_step`, `clauden_file`, `clauden_action` — служебные
     события для интерфейса,
   - `finish_reason` и `[DONE]` — конец.
6. Журнал закрывается, расход записывается в `usage.mjs`.

## Восстановление после обрыва

`GET /v1/turn/active?conversation=c:…` возвращает последний ход. Клиент
проверяет его перед повторной отправкой и забирает готовый текст, если стрим
оборвался. Поэтому двойной запрос не создаёт два ответа и не списывает
лимит дважды.

## Данные на диске

```
data/
  auth.json          аккаунты и сессии
  keys/              API-ключи (хранятся хеши)
  chats/<user>.json  бэкап диалогов
  projects/<user>.json
  memory/<user>.json
  turns/             журнал ходов (TTL 3 дня)
  usage/<user>.json  окна лимитов
  orders/            заказы и данные мест поставщика
  code-sessions/     сессии Code
  workspace/<id>/    файлы сессий Code
```

Всё пишется атомарно (`.tmp` + `rename`). Бэкап — это копия каталога `data`.

## Почему без зависимостей

У шлюза нет `node_modules`: только стандартная библиотека. Это осознанно —
сервер запускается одной командой, обновляется перезапуском процесса и не
тянет цепочку транзитивных пакетов в прод.
